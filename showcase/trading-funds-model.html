Can one model serve a trader's screen and a fund manager's risk list?

The situation

Three product lines — stock trading, mutual funds and structured notes — lived at three different grains. Trades arrive as events; holdings are daily snapshots; fund and note data describe the instrument itself. Every analyst was re-deriving the joins, and every new dashboard rebuilt the same logic slightly differently.

Two audiences pulled in opposite directions. Traders wanted SET Thailand market trends and portfolio performance now. Fund managers wanted one view of recommended funds, AUM, subscriber base and the customers most at risk of redeeming. Pure star schemas kept history clean but made the hot path expensive; pure wide tables were fast but drifted.

Approach

  1. 01

    Separate the grains

    Model trades, daily holdings, instruments and customers as distinct facts with conformed dimensions, so a join cannot silently multiply exposure.

  2. 02

    Build hybrid, not religious

    A Kimball core holds governed history; One Big Table hot paths serve the queries analysts and portfolio teams run all day. Both read from the same definitions.

  3. 03

    Design for the decision

    Trader dashboards expose real-time SET trends and portfolio performance; the fund-holding view puts recommended funds, AUM, subscribers and redemption-risk flags on one screen.

  4. 04

    Make it self-service

    Workshops for traders and analysts, plus a backlog run end to end in Jira and Confluence — user stories, sprint planning and a shared metric vocabulary.
